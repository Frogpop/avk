## 1. Анализ `mul_ijk` и `mul_ikj`

### Исходные функции

```c
static void mul_ijk(void) {
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++) {
            double s = 0.0;
            for (int k = 0; k < n; k++)
                s += a[i][k] * b[k][j];
            c[i][j] = s;
        }
}

static void mul_ikj(void) {
    for (int i = 0; i < n; i++)
        for (int k = 0; k < n; k++) {
            double aik = a[i][k];
            for (int j = 0; j < n; j++)
                c[i][j] += aik * b[k][j];
        }
}
```

Массивы объявлены как двумерные указатели 


#### Внутренний цикл на x86-64

Метка `.L4`:

```asm
.L4:
        mov     rdx, QWORD PTR [r8+rax]      ; rdx = b[k] (загрузка указателя на строку)
        movsd   xmm0, QWORD PTR [rdx+rcx]    ; xmm0 = b[k][j]
        mulsd   xmm0, QWORD PTR [rdi+rax]    ; xmm0 *= a[i][k]
        add     rax, 8                       ; k++
        addsd   xmm1, xmm0                   ; s += a[i][k] * b[k][j]
        cmp     rsi, rax
        jne     .L4                          ; переход назад
```

#### Внутренний цикл на RISC-V

Метка `.L4`:

```asm
.L4:
        ld      a4, 0(a3)                  ; a4 = b[k] (загрузка указателя на строку)
        fld     fa3, 0(a5)                 ; fa3 = a[i][k]
        addi    a5, a5, 8                  ; a5 += 8 (переход к a[i][k+1])
        add     a4, a4, a2                 ; a4 = b[k] + j*8
        fld     fa4, 0(a4)                 ; fa4 = b[k][j]
        addi    a3, a3, 8                  ; a3 += 8 (переход к b[k+1] в массиве указателей)
        fmadd.d fa5, fa3, fa4, fa5         ; fa5 += a[i][k] * b[k][j]
        bne     a1, a5, .L4                ;  переход назад
```

### Какие инструкции загружают `a`, `b`, `c`

| Элемент | x86-64 | RISC-V |
|---|---|---|
| `a[i][k]` | `mulsd xmm0, [rdi+rax]` (загрузка внутри умножения) | `fld fa3, 0(a5)` |
| `b[k][j]` | **две инструкции**: `mov rdx, [r8+rax]` (указатель) + `movsd xmm0, [rdx+rcx]` (значение) | **две инструкции**: `ld a4, 0(a3)` (указатель) + `fld fa4, 0(a4)` (значение) |
| `c[i][j]` | `movsd [r9+rcx], xmm1` (после цикла) | `fsd fa5, 0(a5)` (после цикла) |


### Как меняется адрес `b[k][j]` во внутреннем цикле

Адрес `b[k][j]` меняется с шагом в строку:

- На каждой итерации по `k` компилятор загружает новый указатель `b[k]` из массива указателей.
- между обращениями к `b[k][j]` и `b[k+1][j]` лежит целая строка (`n * 8` байт).

### Количество инструкций в теле внутреннего цикла

| Архитектура | Инструкций |
|---|---:|
| x86-64 | 7 |
| RISC-V | 8 |

Godbolt не поддерживает `-march=native` для RISC-V, поэтому появление векторных инструкций проверить не удалось.


### Почему `ikj` обходит память лучше, хотя число операций то же

Обе функции выполняют одинаковое число умножений и сложений - $n^3$. Разница в порядке обхода памяти.

Матрица в C хранится построчно: элементы `b[k][0], b[k][1], ..., b[k][n-1]` идут подряд в памяти внутри одной строки.

В `ijk` внутренний цикл по `k`. При росте `k` мы берём `b[0][j], b[1][j], b[2][j], ...` - элементы одного столбца. Между ними в памяти лежит целая строка. Более того, так как матрица - массив указателей, на каждой итерации нужно загружать новый указатель `b[k]` из памяти.

В `ikj` внутренний цикл по `j`. При росте `j` мы берём `b[k][0], b[k][1], b[k][2], ...` - элементы одной строки, идущие подряд. Указатель `b[k]` загружается один раз до цикла. То же самое для `c[i][j]`. Одна загруженная кэш-линия (64 байта = 8 `double`) используется 8 раз.

## 2. Штрассен: рекурсия в ассемблере

### Рекурсивные вызовы
Рекурсивный вызов в х86-64:
```asm
call    "strassen_rec(Sub, Sub, Sub, int, int) (.isra.0)"
```
Рекурсивный вызов в RISC-V:
```asm
call    strassen_rec(Sub, Sub, Sub, int, int) [clone .isra.0]
```


### Пролог и эпилог функции

Поскольку функция рекурсивная и имеет много локальных переменных (структуры Sub для A11..C22, указатели на временные буферы, счётчики циклов), компилятор вынужден сохранять множество callee-saved (сохраняемых вызываемым) регистров.
x86-64:

```asm
strassen_rec(...):
    sub     rsp, 392               ; Выделение 392 байт стека (в некоторых клонах 344)
    mov     QWORD PTR [rsp+352], rbp
    mov     QWORD PTR [rsp+384], r15
    mov     QWORD PTR [rsp+376], r14
    mov     QWORD PTR [rsp+368], r13
    mov     QWORD PTR [rsp+360], r12
    mov     QWORD PTR [rsp+344], rbx
    ; ... сохранение остальных переменных в стек
```
Эпилог:
```asm
    mov     rbx, QWORD PTR [rsp+344]
    mov     r12, QWORD PTR [rsp+360]
    ; ... восстановление всех регистров
    add     rsp, 392               ; Освобождение стека
    ret
```

RISC-V:
```asm
strassen_rec(...):
    addi    sp, sp, -272           ; Выделение 272 байт стека (в некоторых клонах 240)
    sd      ra, 264(sp)            ; Сохранение адреса возврата
    sd      s0, 256(sp)            ; Сохранение callee-saved регистров s0-s11
    sd      s1, 248(sp)
    ; ...
    sd      s11, 136(sp)
```

Эпилог:
```asm
    ld      ra, 264(sp)
    ld      s0, 256(sp)
    ; ... восстановление s1-s11
    addi    sp, sp, 272            ; Освобождение стека
    jr      ra
```

### Вызовы malloc / free

Нет, т.к. используются глобальные массивы `tmp_A`, `tmp_B`, `tmp_M`

### Базовый случай

Компилятор вынес проверку базового случая в самое начало функции, до выделения основного кадра стека (в некоторых оптимизированных клонах) или сразу после пролога.

x86-64:
```asm
cmp     ebp, 64          ; ebp содержит размер sz
jle     .L243            ; Если sz <= 64, переход к базовому случаю (вызов naive_sub)
```

RISC-V:
```asm
li      t1, 64           ; Загрузка константы 64
ble     a6, t1, .L68     ; a6 содержит sz.
```

### Почему Штрассен проигрывает на маленьких матрицах?

Хотя асимптотическая сложность Штрассена ниже (O($ n^{2.81} $) против O($n^3$)), на малых  n (например,$n \leq 64$) он проигрывает из-за огромных накладных расходов, которые явно видны в ассемблере:
1. Стоимость пролога/эпилога: На каждом уровне рекурсии процессор выполняет ~10-12 инструкций push/pop (x86) или sd/ld (RISC-V) для сохранения регистров. При глубине рекурсии это даёт тысячи лишних обращений к памяти (стеку).
2. Инструкция call / jal: 7 вызовов функции на каждом уровне. Это не только стоимость самой инструкции, но и сброс предсказателя ветвлений (Branch Predictor) и давление на Return Stack Buffer (RSB), что приводит к штрафам конвейера.
3. Арифметика указателей: Перед каждым вызовом компилятор генерирует блок инструкций (add, imul, lea / add, slli) для вычисления адресов подматриц A11, A12 и смещений в глобальных буферах tmp_A, tmp_M
4. Скалярные циклы сборки результата: Финальные циклы сложения матриц $ M_1 ... M_7 $ в $ C_{11} ... C_{22} $ компилируются в скалярные операции (или частично векторизованные, но с большими накладными расходами на подготовку адресов), в то время как naive для малых матриц отлично ложится в кэш L1 и полностью векторизуется компилятором.

Именно поэтому в коде присутствует `THRESHOLD = 64`: как только размер подматрицы становится достаточно маленьким, выгоднее прекратить рекурсию и выполнить обычное, плотно векторизованное умножение, избежав всех вышеперечисленных накладных расходов.

```c
int max2(int a, int b) {

}

int max3(int a, int b, int c) {

```

## 4. Анализ функции `sum` на RISC-V

Исходный код

```c
long sum(const long *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++)
        s += a[i];
    return s;
}
```

#### Ассемблер RISC-V (`-O2 -march=rv64gc`)

```asm
sum(long const*, long):
        ble     a1, zero, .L4         # если n <= 0, пропустить цикл
        slli    a1, a1, 3             # a1 = n * 8 (размер массива в байтах)
        mv      a5, a0                # a5 = указатель на начало массива
        add     a1, a0, a1            # a1 = a + n*8 (указатель на конец)
        li      a0, 0                 # a0 = 0 (аккумулятор s)
.L3:                                  #  метка начала тела цикла
        ld      a4, 0(a5)             # загрузить *a5 (текущий элемент)
        addi    a5, a5, 8             # a5 += 8 (переход к следующему элементу)
        add     a0, a0, a4            # s += *a5
        bne     a5, a1, .L3           # если a5 != конец, перейти назад
        ret                           # возврат (результат уже в a0)
.L4:                                  # выход при n <= 0
        li      a0, 0                 # s = 0
        ret
```

Пролог

Пролог отсутствует. Функция `sum` - это leaf-функция, поэтому компилятор не создаёт стековый кадр. Все переменные живут в регистрах:

Цикл

Цикл начинается с метки `.L3` и содержит 4 инструкции:

```asm
.L3:
    ld      a4, 0(a5)       # загрузка элемента
    addi    a5, a5, 8       # инкремент указателя
    add     a0, a0, a4      # накопление суммы
    bne     a5, a1, .L3     # условный переход назад
```

Компилятор применил оптимизацию: вместо счётчика `i` и вычисления адреса `a + i*8` на каждой итерации, он инкрементирует указатель на 8 байт и сравнивает его с указателем на конец массива. 

Проверка условия

Проверка `n <= 0` стоит до цикла:

```asm
ble     a1, zero, .L4       # если n <= 0, перейти к .L4
```

Если `n <= 0`, цикл не выполняется ни разу, и функция сразу возвращает `s = 0`.

Эпилог и `ret`

Эпилог отсутствует (нет стекового кадра). Функция просто возвращает результат (результат лежит в а0):

```asm
    ret                         # возврат
```

Почему проверка `n <= 0` стоит до цикла

Исходный цикл:

```c
for (long i = 0; i < n; i++)
    s += a[i];
```

Если `n <= 0`, условие `i < n` ложно с самого начала, и тело цикла не должно выполняться ни разу.

Компилятор генерирует проверку перед циклом, чтобы обработать этот случай:

```asm
ble     a1, zero, .L4       # если n <= 0, пропустить цикл
```

Без этой проверки пришлось бы входить в цикл, проверять условие внутри, и сразу выходить - это лишние инструкции.

## 5. Анализ функции `f`

Исходный код

```c
long f(long n) {
    long s = 0;
    for (long i = 0; i < n; i++) s += i * i;
    return s;
}
```


Ассемблер RISC-V без оптимизаций

```asm
f(long):
        addi    sp, sp, -48           # пролог: выделить 48 байт стека
        sd      ra, 40(sp)            # сохранить адрес возврата
        sd      s0, 32(sp)            # сохранить frame pointer (s0)
        addi    s0, sp, 48            # настроить s0 как frame pointer
        
        sd      a0, -40(s0)           # сохранить n (аргумент) в -40(s0)
        sd      zero, -24(s0)         # s = 0 в -24(s0)
        sd      zero, -32(s0)         # i = 0 в -32(s0)
        
        j       .L2                   # перейти к проверке условия
        
.L3:                                  # ← тело цикла
        ld      a5, -32(s0)           # загрузить i
        mul     a5, a5, a5            # a5 = i * i
        ld      a4, -24(s0)           # загрузить s
        add     a5, a4, a5            # a5 = s + i*i
        sd      a5, -24(s0)           # сохранить s обратно в стек
        ld      a5, -32(s0)           # загрузить i
        addi    a5, a5, 1             # i++
        sd      a5, -32(s0)           # сохранить i обратно в стек
        
.L2:                                  # ← проверка условия
        ld      a4, -32(s0)           # загрузить i
        ld      a5, -40(s0)           # загрузить n
        blt     a4, a5, .L3           # если i < n, перейти к .L3 (тело цикла)
        
        ld      a5, -24(s0)           # загрузить s
        mv      a0, a5                # результат в a0
        
        ld      ra, 40(sp)            # эпилог: восстановить ra
        ld      s0, 32(sp)            # восстановить s0
        addi    sp, sp, 48            # освободить стек
        jr      ra                    # возврат
```

Пролог (4 инструкции)

```asm
addi    sp, sp, -48           # выделить 48 байт стека
sd      ra, 40(sp)            # сохранить адрес возврата
sd      s0, 32(sp)            # сохранить frame pointer
addi    s0, sp, 48            # настроить s0 как frame pointer
```

Размер кадра стека: 48 байт.

Сохраняемые регистры:
- `ra` (return address) — адрес возврата
- `s0` (frame pointer) — указатель на кадр стека

Сохранение переменных в стек:
```asm
sd      a0, -40(s0)           # n → -40(s0)
sd      zero, -24(s0)         # s = 0 → -24(s0)
sd      zero, -32(s0)         # i = 0 → -32(s0)
```

Тело цикла (метка `.L3`, 9 инструкций)

```asm
.L3:
    ld      a5, -32(s0)           # загрузить i
    mul     a5, a5, a5            # a5 = i * i
    ld      a4, -24(s0)           # загрузить s
    add     a5, a4, a5            # a5 = s + i*i
    sd      a5, -24(s0)           # сохранить s
    ld      a5, -32(s0)           # загрузить i
    addi    a5, a5, 1             # i++
    sd      a5, -32(s0)           # сохранить i
```

Эпилог (4 инструкции)

```asm
ld      ra, 40(sp)            # восстановить ra
ld      s0, 32(sp)            # восстановить s0
addi    sp, sp, 48            # освободить стек
jr      ra                    # возврат
```

Почему размер кадра кратен 16


требование ABI (Application Binary Interface) к выравниванию стека на 16 байт.
